Week 10
Reliable Data Transfer: ARQ Protocols

Recall · Week 9

A quick recap

  • Datagrams can get corrupted as they travel through the network.
  • Error detection codes — parity check, Internet checksum, CRC — let the receiver detect whether a packet has been corrupted.
  • Forward Error Correction (FEC) goes further: using error-correcting codes, the receiver can not only detect errors but also correct them without asking for a retransmission.
The bigger picture

What error correction cannot solve

A packet arrives corrupted. The receiver detects the error and discards it — but the sender receives no signal. As far as the sender is concerned, the packet was delivered. It has no idea anything went wrong.

A packet never arrives at all. There is nothing to detect an error in. Error correction is completely silent — and again, the sender has no idea.

Error correction alone is not enough. We need a concrete protocol between the sender and the receiver to address all those problems.

This week

Reliable Data Transfer (RDT)

Reliable Data Transfer (RDT) is the goal: deliver data correctly, completely, and in order to the layer above (typically the application) — no matter what the underlying channel does to it.

For example, suppose the underlying channel is IP. IP is only best-effort: packets might be lost, might arrive corrupted, or might arrive out of order.

If we run an RDT protocol on top of IP, it compensates for all of those risks and still provides correct, complete, in-order delivery.

Outline

We build up reliable data transfer (RDT) protocols one channel assumption at a time:

rdt 1.0 — over a perfectly reliable channel

rdt 2.0 — over a channel with bit errors

rdt 3.0 — over a lossy channel with bit errors

Pipelined reliable data transfer protocols

ARQ

ARQ — Automatic Repeat reQuest

Most RDT protocols are built on a core idea: if the sender does not hear back, it retransmits. Protocols following this pattern are called ARQ (Automatic Repeat reQuest) protocols.

By the end of this lecture, we will learn three ARQ protocols, in increasing sophistication:

  • Stop-and-wait ARQ (a.k.a. rdt 3.0)
  • Go-back-N ARQ (pipelined — more efficient than stop-and-wait)
  • Selective repeat / reject ARQ (pipelined — even more efficient)
rdt 1.0

Reliable data transfer over a perfectly reliable channel

rdt 1.0

Error-free transmission

Start with the easiest case — a perfectly reliable channel:

  • no bit errors
  • no out-of-order frames
  • no frame loss

Nothing can go wrong, so the protocol does nothing clever: the sender sends whenever data is available, and the receiver passes what arrives straight up to its upper-layer protocol.

rdt 2.0

Reliable data transfer over a lossless channel with bit errors

rdt 2.0

A channel with only bit errors

Bits can now be flipped in transit — think of it as a conversation over a bad line.

Here’s one idea: the receiver runs an error detection code — a checksum or CRC — exactly what we learned last week.

If it arrives intact, the receiver sends a positive acknowledgement (ACK).

If an error is spotted, the receiver sends a negative acknowledgement (NAK).

On receiving a NAK, the sender retransmits.

rdt 2.0

What each side does

Sender

  • When a packet arrives from the application, send it and wait for an ACK or NAK.
  • On NAK: retransmit the same packet and wait again.
  • On ACK: move on and wait for the next packet from the application above.

Receiver

  • Packet arrives intact → send an ACK and deliver to the application above.
  • Packet arrives corrupted → send a NAK.

This is the stop-and-wait strategy: the sender transmits one packet, then stops and does nothing until it hears back.

rdt 2.0

The same protocol as a state machine

A finite-state machine says the same thing more precisely: each circle is a state the protocol can sit in, and each arrow is a transition labelled with the event that triggers it and the action taken.

rdt 2.0

A fatal flaw

We assume that the data sent from the sender can be corrupted. But the ACK and NAK messages sent by the receiver also travel back through the same channel — so they can also be corrupted.

Suppose the sender sends “Hello”. The receiver gets it intact and sends back an ACK.

But the ACK gets corrupted in transit.

The sender cannot tell whether the receiver said ACK or NAK. Its only safe option is to resend.

Whenever an ACK or NAK is corrupted, the sender must assume the worst case and retransmit.

rdt 2.0

A fatal flaw

Suppose the sender wants to deliver the message “Zak is his great grandson” from the application above. “Zak is his” arrives intact — receiver delivers it and sends ACK.

“great” arrives intact — receiver delivers it and sends ACK.

The ACK gets corrupted — sender cannot tell, so it resends “great”.

Receiver has no idea this is a resend — it delivers “great” again.

“grandson” eventually gets through and is delivered.

Receiver got: “Zak is his great great grandson”

Regardless, this is the wrong message — it contains a duplicate.

rdt 2.1

The fix: a 1-bit sequence number

Every packet is tagged with a sequence number. For stop-and-wait, a single bit is enough — the sender alternates 0 and 1.

Sender

  • New data: flip the sequence bit and transmit.
  • Retransmission: resend with the same sequence number.

Receiver

  • Packet with the same number as last time → duplicate; discard it, but re-send the ACK.
  • Packet with a different number → new data; deliver it and ACK.
rdt 2.1

Case 1 — a real duplicate

Same story as before: “great” is sent with number 1, and the reply comes back corrupted.

The sender resends “great”, still numbered 1.

The receiver already has number 1, so it discards the copy and just re-acknowledges. Delivered:

“Zak is his great grandson” ✓

rdt 2.1

Case 2 — the data really does repeat

This time nothing is corrupted — but the sender genuinely wants to say “great” twice.

The second “great” carries number 0, not 1 — so the receiver knows it is new data, not a copy.

Delivered:

“Zak is his great great grandson” ✓

rdt 2.2

Numbering the ACKs too

So far the data carries a sequence number but the ACK does not — it just says “yes”, without saying to what.

In stop-and-wait this is actually fine — the sender can only have one packet outstanding at a time, so it always knows which packet the ACK is referring to.

Still, in rdt 2.2 the receiver puts the sequence number in the ACK: “ACK 0” means “I received packet 0”.

With nothing corrupted, the exchange simply alternates:

rdt 2.2

A duplicate ACK is a NAK

“Hello” gets through intact and is acknowledged.

“Everyone” arrives corrupted. Instead of sending a NAK, the receiver re-sends ACK 0 — the sequence number of the last good packet it received.

The sender sees ACK 0 twice. A duplicate ACK can only mean “the next packet did not get through” — so it retransmits.

NAKs are unnecessary: instead of a separate NAK message, the receiver simply re-ACKs the previous sequence number. One message type does both jobs — this is the design TCP uses.

Recap

Quick recap: rdt 2.x

  • rdt 2.x assumes a channel that is prone to bit errors.
  • Every packet carries a sequence number and a checksum; the receiver ACKs each packet with the same number so the sender knows exactly what got through.
  • If the sender receives a corrupted ACK or a duplicate ACK, it simply retransmits.

Next: rdt 3.0 — the channel is not only prone to bit errors, but can also lose packets entirely.

rdt 3.0

Four new ways to fail

Packets can now be lost or badly delayed, not merely corrupted. Four things can happen:

1 · Data lost

2 · ACK lost

3 · Data delayed

4 · ACK delayed

rdt 3.0

How can the sender detect a loss or delay?

The sender uses a timer: send the packet, start a clock, and if nothing comes back, assume the worst and resend.

But how long should it wait?

Too short

The ACK was merely slow, so the sender resends unnecessarily — duplicate packets.

Too long

The sender sits idle long after the packet really was lost — wasted throughput.

In practice, the timer is set to expire after roughly one RTT (round-trip time — the time for a packet to reach the receiver and for its ACK to come back).

rdt 3.0

Timeout and retransmission

The packet is lost, so no ACK will ever arrive.

The sender’s timer expires — loss detected!

It retransmits the same packet, still numbered 0.

rdt 3.0

The timer applies to all other cases too

If the expected ACK does not arrive before the timer expires, the sender retransmits — regardless of why.

ACK lost

ACK delayed

In all three cases the retransmitted data eventually arrives — does this cause the receiver to accept a duplicate?

No — this is fine because the sequence number prevents the receiver from accepting a duplicate.

rdt 3.0

A worked example

The sender wants to deliver two messages to the receiver: Hello, then Everyone.

Suppose Hello, 0 has already been sent. ACK 0 is on its way — but it is delayed.

Timer fires before ACK 0 arrives. What does the sender do?

Recall: if the expected ACK does not arrive before the timer expires, the sender retransmits.

The receiver gets Hello, 0 a second time. What does it do?

Recognises the duplicate — sequence 0 already delivered — and re-sends ACK 0.

The first ACK 0 arrives. What does the sender do?

Move on — send the next packet, Everyone, 1 (flipped sequence number), and restart the timer.

The second ACK 0 now arrives. What does the sender do?

Nothing — it is waiting for ACK 1. The sequence number tells it this ACK is stale.

Performance

The cost of stopping and waiting

rdt 3.0 is correct, but it is still stop-and-wait: one packet, then silence until the ACK returns.

Suppose every packet is L bits, sent at transmission rate R. Therefore, sending each packet takes L/R seconds.

In stop-and-wait, the sender must wait a full RTT (round-trip time — the time for a packet to reach the receiver and for its ACK to return) before it can send again.

Fraction of the time the sender is actually busy:

U = (L/R) ÷ (RTT + L/R)

Performance

How bad is it? A worked example

Take a 1 Gbps link, an RTT of 30 ms, and 1 KB packets.

L/R = 8000 bits ÷ 109 bits/s = 8 µs

U = 0.008 ÷ (30 + 0.008) = 0.00027

The sender is busy 0.027% of the time. Put another way: a gigabit link delivers about 267 kbps — roughly a thousandth of its capacity.

In the next lecture, we will see how sending multiple packets at once — pipelining — keeps the link busy and dramatically improves utilisation.

Recap · Lecture 1

What we covered

rdt 1.0 — over a perfectly reliable channel. No error handling needed: just send and forget.

rdt 2.0 — over a channel with bit errors. The receiver sends ACK or NAK; the sender retransmits on NAK.

rdt 2.1 — adds a 1-bit sequence number to distinguish a resent packet from a new one.

rdt 3.0 — over a lossy channel. A timer triggers retransmission if no expected ACK arrives in time.

All three use a stop-and-wait design — one packet in flight at a time. This causes severe inefficiency: the sender idles for almost the entire round trip.

Week 10 · Lecture 2

Pipelined Reliable Data Transfer

Go-back-N and Selective Repeat

Pipelining

Stop waiting: send several at once

Stop-and-wait — one at a time

Pipelined — several in flight

Consider the sender utilisation U — the fraction of time the sender is actually busy. With three packets in flight:

USW   = (L/R) ÷ (RTT + L/R)

Upipe = 3(L/R) ÷ (RTT + L/R)

In this case, pipelining is 3× more efficient.

Pipelining

What pipelining demands in return

Pipelining is not free. Two things have to grow.

A bigger sequence space

One bit is no longer enough — with several packets in flight the receiver must distinguish more than “this one” from “the next one”. In practice the sequence number is k bits, counting 0 to 2k−1. TCP uses 32 bits.

Buffering

The sender must keep every unacknowledged packet in case it needs to retransmit. Depending on the protocol, the receiver may also be required to buffer out-of-order packets on its side.

In this lecture we will learn about two pipelined protocols: go-back-N and selective repeat.

Go-back-N

Go-back-N

  • The sender keeps a window of up to N unacknowledged packets in flight at once.
  • If any packet is lost or corrupted, the sender resets its progress — it goes back to that packet and retransmits it along with everything that follows — hence the name.
  • What does the receiver do with the packets that arrived after the lost one? Simple: it discards them. It does not buffer any out-of-order packets.
Go-back-N

The sliding window

acknowledged
sent, not yet acknowledged
usable, not yet sent
not usable yet

The data the sender works with: a stream of packets fed from the application layer, each rectangle one packet.

Acknowledged — packets the receiver has confirmed. The sender has delivered these and no longer needs to keep them.

Window of size N — the sender keeps at most N unACK’d packets in flight at once.

Sent, not yet ACK’d — packets currently in transit. The sender holds these in its buffer in case a retransmission is needed.

Usable, not yet sent — within the window, so the sender can transmit these now.

base — points to the oldest unACK’d packet. The window begins here.

nextseqnum — the next packet to transmit.

Go-back-N

The window in motion

Nothing sent yet. The whole window is usable, and base and nextseqnum sit together.

Called from above. Each time the layer above (application layer) hands data to the sender, the sender transmits it and advances nextseqnum. When nextseqnum = base + N, the window is full and no more data can be sent.

An ACK arrives. base advances past everything acknowledged and the window slides right, opening up sequence numbers that were not usable before.

Go-back-N

Cumulative acknowledgements

An ACK n means: every packet up to and including n has been received correctly — not just packet n, but everything before it too. That is what makes it cumulative.

Suppose ACK 1 and ACK 2 are both lost in transit.

ACK 3 arrives — and it alone tells the sender that 1, 2 and 3 all got through, even though ACK 1 and ACK 2 were lost.

Go-back-N

The receiver’s rule in Go-back-N, informally

• The receiver keeps a state: a single number, expectedseqnum — the sequence number of the next in-order packet it expects. (e.g. if it has delivered 4, 5, 6 → expectedseqnum = 7)

• If the arriving packet is the expected one: deliver it and send an ACK.

• Otherwise: discard the packet and re-ACK the last in-order sequence number. The receiver keeps no buffer.

Go-back-N

The receiver in action

The sender pipelines three packets simultaneously — Data A (seq 0), Data B (seq 1), Data C (seq 2) — all in flight at once.

The receiver is waiting for the first in-order packet.

expectedseqnum = 0

Data A (seq 0) arrives. Seq 0 = expectedseqnum — delivered and acknowledged.

expectedseqnum: 0 → 1

Data B (seq 1) is lost. The receiver never sees it.

expectedseqnum = 1

Data C (seq 2) arrives — but seq 2 ≠ expectedseqnum 1. Out of order: discarded. ACK 0 re-sent.

expectedseqnum = 1
Go-back-N

Receiver: the state machine

In-order packet:

if pkt.seq == expected_seq_num:
    deliver(pkt.data)
    send_ack(expected_seq_num)
    expected_seq_num = (expected_seq_num + 1) % seq_space

Out of order or corrupted:

else:
    discard(pkt)
    send_ack((expected_seq_num - 1) % seq_space)
Go-back-N

Timeout: go back N

Just like in rdt 3.0, the channel can lose packets — Go-back-N still needs a timer.

In Go-back-N, the sender uses just one timer for the whole window — set at the oldest unacknowledged packet, base.

When it expires: resend every packet in [base, nextseqnum) — not just the one that timed out.

The reason: if base itself was lost, the receiver — following Go-back-N’s rule — will discard every packet that arrived after the gap. The whole window must go again.

This is why the sender keeps a buffer — a stored copy of every sent-but-unACK’d packet. Without it, go-back-N is impossible.

Go-back-N

The sender’s rule in Go-back-N, informally

• The sender keeps a window of at most N unacknowledged packets, tracked with two variables: base (oldest unACK’d) and nextseqnum (next to send).

• Call from above — application layer requests sending a new packet.

  • If the window is not full (nextseqnum < base + N): assign sequence number nextseqnum to the packet, store it in the buffer, send it, and advance nextseqnum.
  • Otherwise: the window is full — refuse and wait.

• ACK n arrives — advance base to n + 1, and restart the timer (or stop it if nothing is left outstanding).

• Timeout — resend every buffered packet in [base, nextseqnum).

Go-back-N

Sender: the state machine

The sender sits in one Wait state, tracking three things: base (oldest unACK’d), nextseqnum (next sequence number to assign), and pkt_buffer (a copy of every sent-but-unACK’d packet).

Data from app layer:

Recap · Lecture 2

What we covered

  • Sliding window — the sender keeps at most N unacknowledged packets in flight; base and nextseqnum mark the window boundaries, and a pkt_buffer holds every sent-but-unACK’d packet.
  • Receiver rule — the receiver accepts only the next expected packet (expectedseqnum); anything out of order or corrupted is discarded and the last ACK is re-sent.
  • Timeout — one timer covers the entire window; when it fires, the sender restarts the timer and retransmits every buffered packet in [base, nextseqnum).

Selective Repeat

Retransmitting only what was lost

Selective repeat

Selective repeat: resend only what was lost

Go-back-N wastes the network whenever a single packet is lost. Selective repeat fixes that by making the receiver do more work.

The receiver acknowledges every packet individually

Not cumulatively — each ACK names exactly one packet. Out-of-order packets are buffered, not discarded, and delivered upward once the gap is filled.

The sender resends only the packets it has no ACK for

Which means it needs a separate timer for each unacknowledged packet, not one timer for the whole window.

Sender window

N consecutive sequence numbers — still limiting how many sent-but-unacknowledged packets may exist.

Receiver window

N consecutive sequence numbers — the range the receiver is currently willing to accept and buffer.

That second window is new: in go-back-N the receiver had no window at all, just expectedseqnum.

Selective repeat

The sender’s window

acknowledged
sent, not yet acknowledged
usable, not yet sent
not usable yet

Look inside the window: some slots are already acknowledged while earlier ones are not. In go-back-N that was impossible — a cumulative ACK could never leave a hole behind it.

send_base is still the oldest unacknowledged packet, so the window cannot move past it — even though two packets beyond it are safely delivered.

Selective repeat

The receiver’s window

delivered to app layer
not yet received
received & buffered
not yet acceptable

Unlike Go-back-N, the receiver has a window — it can accept and buffer any packet that falls within [rcv_base, rcv_base+N), even if earlier packets have not arrived yet.

rcv_base is the lowest undelivered sequence number. When it finally arrives, the receiver delivers it and all consecutively buffered packets above it — the window slides forward.

Selective repeat

What an individual ACK does

Before. Five packets are outstanding, none acknowledged yet.

ACKs arrive for two of them. Those slots are marked acknowledged — but send_base does not move, because the packet at send_base is still outstanding.

The window advances only when send_base itself is acknowledged — and then it jumps forward past every contiguous acknowledged slot at once.

Selective repeat

Timeout: resend just the one

Each outstanding packet has its own timer. When one expires, the sender resends that packet only and restarts that timer. Everything else in the window is untouched.

Compare go-back-N, where one timer covered the whole window and one expiry resent up to N packets. The extra bookkeeping buys back all that wasted bandwidth.

Selective repeat

The sender’s rules

data received from above

If the next available sequence number falls inside the window, send the packet.

timeout

Every packet has its own timer. Resend that one packet and restart its timer.

ACK received, seq# in [send_base, send_base+N−1]

Mark that packet as received.

If its sequence number equals send_base, advance the base to the next unacknowledged number.

That last condition is the only case in which the sender’s window moves. An ACK for anything else just fills in a slot.

The receiver’s rules

seq# in [rcv_base, rcv_base+N−1]

Send a selective ACK.
If it is out of order, buffer it.
If it equals rcv_base, deliver it together with any buffered packets that follow it consecutively, and advance the window by however many were delivered.

Selective repeat

A dilemma when the window is too big

Suppose the sequence numbers are just 0, 1, 2, 3 and the window size is 3. Consider two different histories.

All three ACKs lost → retransmission

All ACKs arrive → genuinely new data

In both cases a packet numbered 0 arrives at the receiver — and nothing in it says which history produced it. Accept it wrongly and data is duplicated; reject it wrongly and data is lost.

Selective repeat

How big may the window be?

The dilemma arises because the sender’s window and the receiver’s window can drift far enough apart to overlap after wrap-around. Keeping the window small enough prevents it:

window size  ≤  ½ × (size of the sequence-number space)

With sequence numbers 0–3 the space has size 4, so the window may be at most 2 — the example above used 3, which is why it broke.

Recap

Week 10 — what we covered

We built a reliable protocol one channel assumption at a time: rdt 1.0 assumes nothing goes wrong; rdt 2.x adds checksums, ACKs and a sequence number to survive bit errors; rdt 3.0 adds a timer to survive loss.

Stop-and-wait is correct but wastes almost all of a fast link, so we pipelined — several packets in flight, bounded by a window.

Go-back-N keeps the receiver trivial by discarding anything out of order, and pays for it by resending the whole window. Selective repeat buffers and acknowledges individually, resending only what was lost.

Both are sliding-window protocols; they differ only in how much they throw away.
