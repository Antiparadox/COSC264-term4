Why multiplexing is needed

The network layer — IP — only ever looks at IP addresses. To it a host is a single object at a single address; it has no view of the sockets inside.

So when a packet arrives, IP can deliver it to the host — but it cannot tell which socket the data inside should go to.

The transport layer coordinates this traffic in both directions so each socket gets exactly its own data. This is known as multiplexing/demultiplexing.

UDP communication model

UDP is unreliable and connectionless

Unreliable. UDP does not guarantee delivery, ordering, or protection against duplicates.
Connectionless. A sender does not set up a connection before sending.
Why not? Because UDP identifies the socket by the destination alone. Put a destination IP address and port in the header, and UDP hands the datagram to that socket.
It does not care where the datagram came from, so there is no binding between a particular sender and a particular receiver.

Why do some applications choose UDP?

No setup delay

An application can send immediately because UDP does not establish a transport connection first.

2

Since UDP is connectionless, it keeps no per-connection state — no buffers, sequence numbers or windows.

3

Small header

Every UDP message adds only an eight-byte transport header.

4

Application control

UDP provides no reliability, so the application decides when to send and builds whatever recovery it needs — rather than taking TCP’s fixed mechanism.

TCP communication model

TCP is reliable and connection-oriented

Reliable. TCP delivers the byte stream without loss, duplication or reordering — it has an RDT mechanism built in.
Connection-oriented. TCP identifies a connection by four values: source IP address and port, destination IP address and port.
So a sender must first run a handshake to set the connection up before it may send any data, and that connection ties one particular sender to one particular receiver.

TCP communication model

If several clients want to talk to the same server, they each get their own connection — and so their own connected socket on that server.
Compare with UDP: being connectionless, it lets many clients share a single socket.

TCP establishes a connection with a three-way handshake

1 · SYN. The client sends a segment with the SYN flag set, asking to open a conversation.
2 · SYN + ACK. The server agrees: in one segment it sets its own SYN flag and an ACK for the client’s request.
3 · ACK. The client acknowledges the server’s half, and the connection is open.
Now that both sides have heard from each other, they can start sending packets to one another.

Pipelining · cumulative acknowledgments · retransmission

The RDT used by TCP — an overview

TCP uses a reliable data transfer protocol on top of IP to provide reliable, in-order byte delivery.

Its RDT is inspired by both Go-Back-N and Selective Repeat — the pipelined protocols we studied in Week 10.

Pipelining and cumulative acknowledgments

The TCP sender uses a window of segments in flight, for pipelining.

The TCP receiver keeps a buffer, as in Selective Repeat, and acknowledges with cumulative ACKs, as in Go-Back-N.

But unlike Go-Back-N — where the ACK names the last in-order segment received — TCP's ACK names the next byte expected.

Loss recovery

Retransmission happens when the timer times out or when duplicate ACKs arrive (fast retransmit).

Byte stream · every byte has its own number

TCP sequence numbers count bytes

Byte-level addressing

In the RDT protocols from Week 10, each sequence number advanced by one packet — between consecutive sender messages, the sequence number advanced by one.

In TCP, sequence numbers address individual bytes — so between consecutive sender segments, the sequence number advances by the number of bytes in the segment.

Maximum Segment Size (MSS)

The largest payload a single TCP segment can carry — negotiated during the handshake. Typical value: 1460 bytes on Ethernet (1500 MTU − 20 IP − 20 TCP).

SYN and FIN consume a sequence number

SYN and FIN each consume exactly one sequence number, even though they carry no application data — this ensures they can be reliably acknowledged.

ISN = 1000 · MSS = 1000 bytes · 3000 bytes to send

The TCP sender rules: overview

Data from application

Divide the byte stream into segments, typically 1 MSS bytes each.

Number each segment by its first byte, counting on from the initial sequence number (ISN) chosen in the handshake.
e.g. ISN = 1000 and 1 MSS = 1000 bytes, so the segments start at 1001, 2001, 3001, …

As in any pipelined RDT, the sender keeps a send window.
e.g. a window of 5 MSS, i.e. 5 segments.

Suppose the first two segments have already been acknowledged, so the window base starts at the third segment, seq 3001. The sender may send anything within the window, so segments 3001–7001 go out.

Then start one timer, if none is running.

ACK received

A cumulative ACK slides the window forward.

Restart the timer if unacknowledged data remains; stop it if everything is confirmed.

e.g. the sender receives ACK 5001: the receiver is expecting the segment starting at 5001.

Since ACKs are cumulative, segs 3001 and 4001 are both acknowledged.

So the window base moves to 5001, and the window now covers 5001–9001.

Segs 8001 and 9001 can now go out, and the timer restarts on 5001.

Timeout

Retransmit only the oldest unacknowledged segment, then restart the timer.

This is different from Go-Back-N. Recall that in GBN, the sender retransmits every in-flight packet in the window; TCP retransmits only one.

e.g. here GBN would retransmit all five segs, 5001–9001; TCP retransmits only seg 5001.

TCP reliable data transfer

TCP fast retransmit

The problem

Timeout period is relatively long. Suppose seg 6001 is lost — in Go-Back-N, the sender must wait until timeout before it can retransmit. This can take a long time.

Duplicate ACKs — an early signal

The receiver ACKs the last in-order byte. When 7001, 8001, and 9001 arrive but 6001 is missing, each generates another dup ACK 6001.

A stuck ACK (not advancing) means the receiver is still waiting for the same segment — already an early indication of loss, before the timer fires.

Fast retransmit

After 3 duplicate ACKs, retransmit the missing segment immediately — without waiting for the timeout.

TCP reliable data transfer

TCP receiver rules: overview

Like Go-Back-N: cumulative ACK

The receiver sends a cumulative ACK for the highest in-order byte received. If a segment arrives out of order, the receiver sends a duplicate ACK — ACKing the next expected sequence number, signalling the gap to the sender.

Like Selective Repeat: receiver buffer

Unlike Go-Back-N, the receiver buffers out-of-order segments within the receive window rather than discarding them. Once the missing segment arrives and the gap is filled, buffered data is delivered to the application in order.

Further improvements

There are further recommendations for ACK generation (e.g. to avoid sending too many ACKs) in RFC 1122 and RFC 2581.

TCP can also negotiate selective ACK options [RFC 2018] — the receiver reports exactly which byte ranges it holds, letting the sender retransmit only the missing pieces, much like Selective Repeat.

TCP reliable data transfer

TCP timeout: the challenge

The timer should track RTT

The sender's retransmit timer is set to roughly the round-trip time —

just long enough for a packet to receive its ACK. Too short → spurious retransmissions waste bandwidth. Too long → slow recovery when a segment really is lost.

The problem: RTT is not a constant number in the real world

Network load, queueing, and path changes cause RTT to fluctuate — sometimes dramatically.

A fixed timeout value cannot adapt.

This is why TCP estimates RTT dynamically, in real time, and updates its RTT estimate continuously.

TCP reliable data transfer

TCP RTT estimation

SampleRTT

EstimatedRTT is derived by taking many individual RTT samples.

Each sample is measured from when a segment is transmitted until its ACK is received.

Retransmitted segments are excluded: the ACK could be for the original send or the retransmit — the sender cannot tell, so the measurement would be unreliable.

EstimatedRTT — exponential weighted moving average

SampleRTT varies noticeably from measurement to measurement. So how does TCP smooth out these variations and derive EstimatedRTT from the samples?

TCP uses a smoothing technique that computes a smooth, adaptive estimate from the samples.

EstimatedRTT = (1−α)·EstimatedRTT + α·SampleRTT

Typical value: α = 0.125. Unrolling this one step at a time:

EstimatedRTT = α·Samplen + α(1−α)·Samplen−1 + α(1−α)2·Samplen−2 + …

Each step further back adds another factor of (1−α) = 0.875 — so older samples count exponentially less.

This is why it is known as an exponential weighted moving average: it smooths out SampleRTT to produce EstimatedRTT.

TCP reliable data transfer

TCP timeout interval

You might be tempted to simply set the timeout interval to EstimatedRTT.

In practice, this turns out to be too aggressive: due to exponential averaging, EstimatedRTT takes some time to adapt to the real-time RTT.

So when the real RTT suddenly spikes — say the network becomes congested — EstimatedRTT has not caught up yet, and the timer fires too early.

We therefore need a safety margin for RTT variability. How do we choose it?

DevRTT — tracking variability

We also maintain DevRTT — a tracker for how much SampleRTT deviates from EstimatedRTT.

DevRTT = (1−β)·DevRTT + β·|SampleRTT − EstimatedRTT|

Typical value: β = 0.25.

TimeoutInterval

This is how TCP sets the timeout interval, with DevRTT providing the extra safety margin:

TimeoutInterval = EstimatedRTT + 4·DevRTT

Empirically, this prevents the timer from firing too early in the case of a sudden spike in RTT.

Matching the sender to the receiver and the network

TCP Flow Control and Congestion Control

TCP traffic management

Flow control vs congestion control

What are flow control and congestion control? Consider a sender transmitting data to a receiver. The router in the middle stands for the network in between.

Ideally, the sender would send data as fast as it likes. In practice it cannot: there are two bottlenecks that could occur.

Flow control

In our previous discussions, we always assumed that the application consumes data as soon as it arrives at the receiver.

In reality, the application may read slowly, so the receiver must hold incoming data and feed it to the application gradually. This is why the receiver maintains a receive buffer.

This buffer has a limited size: if the sender transmits too fast, it overflows and segments are lost.

Flow control prevents this by matching the sender’s transmission rate to the speed at which the receiver’s application reads, so the buffer does not overflow.

Congestion control

We have already seen that datagrams travel through the Internet across a series of routers.

A router takes time to process each incoming datagram and cannot always forward it immediately, so it keeps a router buffer.

If too many senders transmit simultaneously, the buffer of some router along the route fills up and segments are dropped: the network is congested.

Congestion control prevents this by limiting each sender’s rate to match what the network can carry.

Speed-matching the sender to the receiver

TCP flow control: the receive window

The receive buffer and floating window

The receiver allocates a fixed-size receive buffer (RcvBuffer) for the connection. Incoming data sits there until the application reads it.

Recall that in RDT, the receiver window is the range of packets the receiver is willing to buffer.

In our previous discussions, we assumed the application consumes data as soon as it arrives. The buffer was therefore always fully available to receive, so we always set receiver window = buffer size.

In TCP, the application reads at its own pace — so the buffer may contain unread data that reduces available space.

The unread portion is then [LastByteRcvd − LastByteRead]; thus the receiver window floats:

RcvWindow = RcvBuffer − [LastByteRcvd − LastByteRead]

e.g. RcvBuffer = 4000 bytes, LastByteRead = 2000, LastByteRcvd = 3500 → RcvWindow = 4000 − (3500 − 2000) = 2500 bytes.

LastByteRcvd: the sequence number of the last byte received.

LastByteRead: the sequence number of the last byte the application has read.

From receiver to sender

Advertising and enforcing the receive window

Advertising the window

How does the TCP receiver advertise its current window to the sender?

In TCP, the receiver piggybacks RcvWindow on every segment it sends, carried in the Receive Window field of the TCP header.

The TCP sender’s rule

LastByteSent − LastByteAcked ≤ RcvWindow

Recall from our earlier discussion: LastByteAcked is essentially the window base, and LastByteSent is essentially nextseqnum. So the left side counts the bytes in [base, nextseqnum) — the data in flight.

Recall that in RDT, the sender window N capped the data in flight. The TCP sender works the same way, but its cap is not a fixed N: it is the RcvWindow the receiver advertises.

Flow control · corner case

A corner case: the zero window

The problem

Suppose B’s receive buffer fills up, so B advertises RcvWindow = 0. A must stop sending.

Later, B’s application reads the buffered data. The buffer empties, so B’s window is open again: RcvWindow > 0.

But A has not heard about it. Its latest information is still RcvWindow = 0, so A still cannot send.

And B cannot tell A: with no data of its own, B only sends a segment (an ACK) in reply to one from A. A waits for B, B waits for A — a deadlock.

The solution

While RcvWindow = 0, A keeps sending tiny segments carrying just 1 byte of data.

B must acknowledge each one, and every ACK carries B’s current RcvWindow — so as soon as space frees up, A learns it and resumes sending.

Congestion control

Approaches to congestion control

Network-assisted

Routers explicitly notify senders to slow down.

This requires the routers along the path to cooperate — e.g. a router sets a congestion bit in the IP packet header, or states the rate it can support.

End-to-end

No explicit feedback from the network: the sender infers congestion from signals it can observe itself.

e.g. a timeout, or duplicate ACKs. TCP treats these as loss events.

TCP uses the end-to-end approach — congestion is inferred from loss events in the network.

Congestion control

TCP congestion detection and action: an overview

The congestion window

Flow control already caps the data in flight at RcvWindow.

Congestion control adds a second cap on the same quantity: the congestion window (CongWin), which the sender sets itself and adjusts up and down with the level of congestion.

LastByteSent − LastByteAcked
≤ min(CongWin, RcvWindow)

The data in flight must respect both caps.

Sending

As long as there is room in the window (data in flight < CongWin), the sender can send more data.

Detection and action

The sender observes a loss event, e.g. three duplicate ACKs or a timeout.

On a loss event, the sender shrinks CongWin.

If no loss event is observed, the sender slowly increases CongWin.

Congestion control

TCP sending rate: a per-RTT view

What the sender controls

The previous frame gives a discrete rule: keep data in flight ≤ CongWin. But how does the sender actually obey that rule?

It turns out that what the sender can actually control is its own sending rate. Since the TCP sender sends data as a byte stream, the sending rate is measured in bytes per second.

If the sending rate is too high, the data in flight exceeds CongWin. So how should the sender set its sending rate, subject to the in-flight constraint?

The missing ingredient: RTT

Recall: the sender transmits segments back-to-back — all remain in flight until the first ACK returns, which takes one RTT.

So within one RTT, everything sent is simultaneously in flight. Since at most CongWin bytes can be in flight, the sender can send at most CongWin bytes per RTT.

The sending rate

So the sender should send CongWin bytes per RTT, i.e. set its sending rate to:

sending rate ≈ CongWin / RTT  bytes/sec

Congestion control

Setting the congestion window

How does the TCP sender decide how to set its congestion window?

It depends on where the connection is in its life. There are two cases, and each gets a different treatment.

Case 1: just after the connection is set up

The three-way handshake has just finished. The sender knows nothing yet about how much the network can carry, so it starts by setting CongWin small and increases it very quickly.

This phase is called slow start.

Case 2: a while after the connection is set up

CongWin has already grown large, close to what the network can carry. Now the sender should grow it carefully, to avoid causing congestion.

This phase is called congestion avoidance.

Congestion control

TCP · slow start

Starting conservatively

When a connection begins, the sender knows nothing about the path — start conservatively: CongWin = 1 MSS.

Since CongWin = 1 MSS, the in-flight constraint means the sender may only send 1 MSS per RTT.

Each segment carries exactly 1 MSS of data. Send one segment, wait for its ACK.

Growing the window

Each ACK confirms the network handled the segment — likely no congestion yet.

Slow-start rule

For every ACK received: CongWin += 1 MSS

CongWin increases to 2 — in the next RTT the sender can send 2 MSS.

Two more ACKs received — each adds 1 MSS. CongWin increases to 4, and in the next RTT we can send 4 MSS.

The pattern: the growth rate depends on the current window size.

Slow-start empirical rule

CongWin doubles every RTT — 1, 2, 4, 8, 16… — exponential growth

The threshold

Exponential growth can't last forever. A threshold called ssthresh (slow-start threshold) marks where slow start ends.

When CongWin ≥ ssthresh → switch to congestion avoidance (next frame).

Congestion control

TCP · congestion avoidance

Additive increase

Once CongWin ≥ ssthresh, growth switches from exponential to linear.

Additive increase

If no loss detected: CongWin += 1 MSS per RTT

Example. Suppose ssthresh = 4 MSS, and CongWin has just reached it: CongWin = 4 MSS.

In the first RTT, the sender sends 4 segments.

Once all 4 are acknowledged, CongWin grows by just 1 MSS — not doubled to 8 — so CongWin = 5, and the next RTT carries 5 segments.

And so on: after those 5 are acknowledged, CongWin = 6, then 7, … one MSS per RTT.

We keep doing additive increase, but this cannot last forever: eventually the network becomes congested again, and the sender hits a loss event.

What should the sender do then?

Multiplicative decrease

Multiplicative decrease

Upon loss event: CongWin = CongWin / 2

Together, this is known as the AIMD rule — Additive Increase, Multiplicative Decrease.

Congestion control

Why AIMD?

Why this particular combination? Let’s consider some alternative designs to AIMD. Here are a few options.

Multiplicative Increase, Additive Decrease (MIAD)

Multiplicative increase overshoots capacity aggressively, while additive decrease backs off too slowly — congestion persists.

Additive Increase, Additive Decrease (AIAD)

Does AIAD control congestion correctly? For a single flow, yes.

But here is what goes wrong: a different issue, fairness. The goal of fairness is that every flow sharing a bottleneck link should converge to an equal share of bandwidth.

Suppose two flows share a 10 Mbps link: Flow A = 8 Mbps, Flow B = 2 Mbps. This is not fair — a good congestion control design should correct the imbalance while also preventing congestion.

Additive increase: both add 1 Mbps → A = 9 Mbps, B = 3 Mbps. Total exceeds capacity → loss.

Additive decrease: both subtract 1 Mbps → A = 8 Mbps, B = 2 Mbps. Back to the start — the unfairness never corrects.

AIAD does not solve the fairness problem.

Additive Increase, Multiplicative Decrease (AIMD)

Additive increase probes gently; multiplicative decrease reacts sharply. Converges to both efficiency and fairness.

Take-home question: using the same example (A = 8 Mbps, B = 2 Mbps), why does multiplicative decrease close the gap where additive decrease could not?

Congestion control

TCP · reacting to loss

What a loss event changes

We said TCP cuts CongWin in half on a loss. That is not the whole truth: there are two kinds of loss event.

What every loss event changes is the slow-start threshold, our empirical estimate of the network’s capacity. It is set to half the CongWin at which the loss occurred:

On any loss event

ssthresh = CongWin / 2

What happens to CongWin itself depends on the loss signal. There are two cases.

Case 1: Timeout

A timeout signals severe congestion: the sender hears nothing back at all.

So be conservative and start from scratch: reset CongWin = 1 MSS and enter slow start.

Case 2: Three duplicate ACKs

Three duplicate ACKs signal a milder loss: the receiver is still replying, so some data was lost but packets are still getting through.

So the sender enters fast recovery, and eventually CongWin is cut only to ssthresh, half its old value.

This is the TCP Reno design. In TCP Tahoe, there is no distinction: both cases reset CongWin = 1 MSS and enter slow start.

Congestion control

TCP · fast recovery

Suppose CongWin = 6. Segments 1–3 have been acknowledged, and the sender has more data to transmit.

The sender fills the congestion window: segments 4–9 are now in flight.

The sender then receives three dup ACKs for segment 4. What does this mean?

Segment 4 is likely lost during transmission. But importantly, three ACKs means three of the in-flight packets 5–9 reached the receiver — suppose those are segments 5, 6, 8.

What should the sender do now?

Fast retransmit: immediately resend segment 4.

The sender enters fast recovery.

Fast recovery — enter ssthresh = CongWin / 2 = 3 CongWin = ssthresh + 3 = 6 Why inflate by 3?

• CongWin limits how many segments can be in flight. If we simply apply AIMD and set CongWin = ssthresh = 6/2 = 3, the window starts at base 4 and covers segments 4, 5, 6.

• However, by observing 3 dup ACKs, we know 3 segments among 5–9 are no longer in flight. Segments 5, 6, 8 are confirmed received and do not occupy in-flight slots.

• The only truly in-flight segments are 4, 7, 9. This justifies inflating CongWin to 6 = ssthresh (3) + confirmed received (3), reflecting that only 3 segments are truly in flight.

Fast recovery — per dup ACK

For each additional dup ACK: CongWin += 1 MSS

For the same reason, each additional dup ACK signifies one less segment is truly in flight — the window can grow by 1.

Segment 7 received, yet segment 4 still pending (another dup ACK for 4): CongWin = 7 — can now send segment 10.

Segment 9 received, yet segment 4 still pending (another dup ACK for 4): CongWin = 8 — can now send segment 11.

TCP · fast recovery exit

Now suppose the retransmitted segment 4 has been received, so the receiver sends a cumulative ACK for everything through segment 9 — it sends ACK 10.

Fast recovery — exit rule

On new ACK:

• Set CongWin = ssthresh

• Enter congestion avoidance

The sender receives ACK 10. Base advances to segment 10. CongWin = ssthresh = 3 — the inflated window deflates back to the halved value.

Enter congestion avoidance. Fast recovery is complete.

Flow and congestion control

Flow and congestion control — summary

Flow control: the receiver advertises RcvWindow in every segment, so a fast sender cannot overflow a slow receiver’s buffer.

Congestion control: the TCP sender maintains a CongWin, and keeps its data in flight within both caps: LastByteSent − LastByteAcked ≤ min(CongWin, RcvWindow).

TCP begins in slow start, doubling CongWin each RTT until ssthresh, then grows linearly in congestion avoidance.

Three dup ACKs trigger fast recovery — ssthresh and CongWin halve. A timeout drops CongWin to 1 MSS and restarts slow start.
