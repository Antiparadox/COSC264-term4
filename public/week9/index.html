Internet checksum

One’s complement arithmetic

The checksum uses two operations:

One’s complement addition

  1. Add the two numbers as unsigned integers.
  2. If there is a carry out of the leftmost bit, add 1 to the sum (end-around carry).
ex1.  (no carry)
  A2B3
+ 1D4C
  BFFF
ex2.  (carry out)
  A2B3
+ 6F8E
 carry → 11241
+    1 ← end-around

One’s complement operation

Replace every 0 bit with 1 and every 1 bit with 0.

   1111 → ones complement → 0000
   1001 → ones complement → 0110

Adding a value and its one’s complement always gives all 1s:

1001 + 0110 = 1111

Internet checksum

Sender computation

1. Take the IP header.

2. Split it into 16-bit words.

3. Compute their one’s-complement sum.

4. Take the one’s complement of that sum — that is the checksum.

IPv4 header rows are 32 bits wide. Our simplified header is one such row, written in hex:

F2345678

F234 5678

32 bits → two 16-bit words

The sum overflows 16 bits, so the carry 1 is wrapped around and added back at the low end — the end-around carry of one’s-complement addition.

Internet checksum

Receiver verification

1. Take the received header — the checksum field now holds B752.

2. Compute the one’s-complement sum of the header words.

3. Add the checksum to that sum.

4. The check succeeds if the result is all 1 bits (FFFF).

F234 5678 B752

Why all 1s? The sender set the checksum to the one’s complement of exactly this sum. Adding a value to its own one’s complement always gives all 1 bits — so if nothing changed in transit, the total must be FFFF.

Result = FFFF → no error detected.

Internet checksum

Efficiency and limitations

The primary reason for its adoption is efficiency:

  • Most of these protocols are implemented in software
  • The Internet checksum involves simple operations → very little computational overhead

But it also has a limitation:

  • It is much less effective at detecting errors than a stronger code such as the cyclic redundancy check (CRC)
  • The Internet checksum is therefore an additional, cheap check — not the primary defence

The CRC is the subject of the next concept.

Recap

Error detection — what we covered

Why error detection is needed: a datagram’s contents often get corrupted in transit, so the receiver needs a way to tell whether what arrived is what was sent.

How it is done: the sender attaches redundant bits computed from the data — an error-detection code.

We studied two of them:

Parity check — add parity bits so the number of 1s comes out even; simple, and in two dimensions it can even correct a single-bit error.

Internet checksum — send the complement of the one’s-complement sum of the header’s 16-bit words; cheap in software, used by IPv4 and TCP/UDP.

Error Detection

Cyclic Redundancy Check (CRC)

The CRC is one of the most common and most powerful error-detecting codes in use.

It lives in the data link layer — the layer just above the physical medium, responsible for moving a frame across a single link. Every frame you send over Ethernet or Wi-Fi carries a CRC.

Application
Transport  (TCP/UDP)
Network  (IP)
Data link
CRC lives here

CRC

How it works — the idea

Start with a k-bit message. Sender and receiver agree in advance on a fixed divisor.

Trans­mitter

Compute an (n−k)-bit Frame Check Sequence (FCS) and append it to the message, so that the resulting n-bit frame is exactly divisible by the agreed divisor.

Receiver

Divide the received n-bit frame by the same divisor. No remainder → assume no error. Non-zero remainder → the frame was corrupted, so discard it.

CRC

CRC — notation

  • D — the k-bit block of data to send
  • F — the (n−k)-bit FCS we must compute
  • P — the predetermined divisor, a fixed pattern of n−k+1 bits — one bit longer than F
  • T — the n-bit frame actually transmitted: D followed by F

We want T to be exactly divisible by P. To achieve that, F must be set to:

F = remainder of (D × 2n−k) / P

CRC

How to choose the pattern P?

P is chosen to be one bit longer than the desired FCS.

But not every pattern of that length will do — two clearly bad choices:

  • P = 0000…0 — you cannot divide by zero at all.
  • Highest-order bit of P = 0 — the leading zero contributes nothing to the division, so P is effectively one bit shorter. And since the FCS is always one bit shorter than P, the effective FCS is one bit shorter too — fewer check bits than we intended.

The exact bit pattern depends on the type of errors expected — but in every case:

REQUIRED

The highest-order bit = 1

REQUIRED

The lowest-order bit = 1

This is what buys the burst-error guarantee — we will see why shortly.

CRC

Modulo-2 Arithmetic

  • Addition and subtraction are both performed with XOR (⊕) — so they are the same operation.
  • Multiplication is the usual shift-and-add — only the additions inside it become XORs.
  • Ordinary binary addition propagates a carry: 1 + 1 = 10. In modulo-2 there are no carries and no borrows — each bit position stands on its own: 1 ⊕ 1 = 0 and 0 ⊕ 1 = 1.

CRC

One more way to write the same thing

The divisor P — the pattern both sides agree on in advance — is also called the generator of the code, because it is what generates the FCS.

Generators are almost never written as bit strings. They are written in the polynomial representation — and a code built this way is called a polynomial code. There are two reasons to learn this form:

1. Every CRC standard writes its generator this way. Look up the one Ethernet uses and you will find x32 + x26 + x23 + …, not a row of 33 ones and zeros.

2. It is the form in which you can analyse which errors a given generator will detect. We will touch on this briefly, but it is beyond the scope of this course and will not be examined.

CRC · optional

What can this representation tell us?

Optional material, for anyone curious about why the polynomial form is used. Not examined.

A corrupted frame can always be written as T(x) + E(x), where the error polynomial E(x) has a 1 in every flipped position.

We built T(x) to divide evenly by P(x). So the corrupted frame divides evenly — and the error slips through — exactly when P(x) divides E(x).

So we choose a generator P(x) that cannot divide the error patterns we expect. For most E(x), the division simply does not go through.

CRC · optional

Example: a short burst error

Suppose interference corrupts a short run of adjacent bits in our transmitted frame:

E(x) = x2 + x + 1

degree 2 — while P(x) = x5 + x4 + x2 + 1 has degree 5

The degree of a polynomial is just its highest power — equivalently, the position of its leading 1 bit.

A degree-5 polynomial cannot divide a non-zero polynomial of degree 2. So the remainder cannot be zero and the burst is always caught.

The same conclusion holds wherever the burst sits in the frame, as long as it is shorter than P.

CRC

Some Standard Polynomials

These trade-offs have already been worked out. Always use a standard generator — never invent your own.
Four versions of P(X) are widely used:
  • CRC-12: transmissions of streams of 6-bit characters
  • CRC-16 / CRC-ANSI: various communication protocols, including serial standards like Modbus
  • CRC-CCITT: telecommunications applications
  • CRC-32 / IEEE-802: network protocols — Ethernet, ZIP, PNG, and other file transfer protocols
CRC-12 = X12 + X11 + X3 + X2 + X + 1
CRC-ANSI = X16 + X15 + X2 + 1

Recap

CRC — what we covered

The CRC is an error-detection code: it appends a Frame Check Sequence chosen so that the whole frame divides exactly by an agreed generator P, and the receiver simply checks for a zero remainder.

All of the arithmetic is modulo-2 — addition, subtraction and division are XOR, with no carries and no borrows.

Generators are conventionally written as polynomials, and the standard ones are chosen for the error patterns they are guaranteed to catch.

CRC · Limits

When detection is not enough

Everything we’ve seen so far — parity, checksum, CRC — can detect errors. When an error is detected, the standard response is to ask the sender to retransmit.

Wireless links

High bit error rate — constant retransmissions overwhelm the link.

Satellite links

Propagation delay ~500 ms RTT — waiting for retransmission is too slow.

→ Next we’ll see how to design codes that let the receiver correct errors directly — no retransmission needed.

Error correction

Forward Error Correction (FEC)

→
Typically, retransmission is needed when bit errors are detected.
→
Not good enough for wireless applications:
  • High bit error rate (BER) on a wireless link
  • Long propagation delay on satellite links
→ Need to correct errors on the basis of the bits received — without retransmission.
FEC

The FEC process — sender

The message is divided into blocks of k bits — each one a data block.

The encoder is applied to each data block independently, turning every k-bit block into an n-bit codeword — the extra n−k bits are the redundancy.

The codewords are then transmitted, one after another.

FEC

The FEC process — receiver

The receiver splits the incoming stream back into n-bit codewords — some of which may have been corrupted in transit.

The decoder is applied to each codeword independently.

Each decode recovers the original k-bit data block, correcting any errors the code is strong enough to fix.

The recovered blocks are reassembled into the original message.

All of this happens at the receiver — no retransmission is needed.

FEC

Block Code Principles — Hamming Distance

The Hamming distance d(v₁, v₂) between two n-bit binary sequences is the number of bit positions in which v₁ and v₂ disagree.
Example:
v₁ = 0 1 1 0 1 1
↕ · ↕ · ↕ ·
v₂ = 1 1 0 0 0 1
3 positions differ  →  d(v₁, v₂) = 3
FEC

How the encoder and decoder work

The design of the encoder and decoder is what determines how many errors an FEC scheme can detect and how many it can correct — it is the most important aspect of the whole process.

There are many ways to design an encoder — different codes assign different codewords to the same data blocks, and we will not go into how they are constructed.

But whatever the code, the decoder works in the same way. Given the received n-bit pattern:

1. Is it one of the valid codewords?

If so, no error is detected — output the data block the encoder assigned to it.

2. If not, an error has occurred — that much we know immediately.

Then find the valid codeword closest to it in Hamming distance, and output that codeword’s data block as the recovered data. This is minimum-distance decoding.

The reasoning behind step 2 is simply that fewer bit flips are more likely than many — so the nearest valid codeword is the most plausible thing the sender actually transmitted.

FEC

The full picture for this code

With n = 5 there are 25 = 32 possible received patterns:

000000000100010…00111…11001…1111011111

Only four of them are valid codewords, so 28 are invalid.

20 of the 28 lie at distance 1 from a valid codeword — four codewords × five single-bit flips each. So far, nothing surprising.

What matters is that each of those 20 is at distance 1 from exactly one codeword — never two. The nearest codeword is unique, so all 20 can be uniquely decoded and corrected.

The remaining 8 are not so lucky: each lies at distance 2 from two different codewords, so the nearest one is not unique and they can only be detected:

01010 01011 01100 01101 10010 10011 10100 10101

So this code corrects any single-bit error and detects any double-bit error.

We counted that out by hand for one small code. For a general code, how many errors can it correct, and how many can it detect?

FEC

It comes down to a single number: the minimum Hamming distance d of the code — the smallest distance between any two valid codewords.

FEC

Walking away from a codeword

Picture the whole space of bit strings as a grid: every node is one specific bit string, and any two adjacent nodes differ in exactly one bit — Hamming distance 1.

Two codewords A and B that achieve the minimum sit on this grid d steps apart.

Send A over a channel that flips at most k bits. Each flip is one step to a neighbour, so the received pattern lands somewhere within k steps of A.

The further it drifts from A, the less it looks like A — and the more it may start to resemble some other codeword.

The worst case is when every flip takes us straight towards the nearest codeword B, so the pattern looks more and more like B with each step.

FEC

When can the error still be corrected?

While k ≤ ⌊(d−1)/2⌋ the pattern stays inside A’s region and never crosses the halfway line, so A is still strictly the nearest codeword — minimum-distance decoding walks us back to A. Corrected.

On the halfway line the pattern is equidistant from A and B. It could have come from either, so the decoder cannot say which was sent — correction is no longer possible.

FEC

Past halfway, we can still detect

  • Suppose the channel flips more than ⌊(d−1)/2⌋ bits, so correction is out of reach.
  • As long as it flips fewer than d bits, we cannot reach B — B is a full d steps away.
  • And B is the nearest codeword to A, so if we cannot reach B we cannot reach any codeword.
  • So wherever the pattern lands, it cannot be a valid codeword.
  • The receiver sees a non-codeword and reports an error — the error is detected, even though it cannot be corrected.
FEC

The rule

A code with minimum Hamming distance d

• corrects up to ⌊(d−1)/2⌋ bit errors

• detects up to d − 1 bit errors

For the code we have been working with, d = 3 — so it corrects 1 error and detects 2.

So a good FEC code is designed to make its minimum distance as large as possible — the larger d is, the more errors it can correct and detect.

Recap

Error correction — what we covered

Forward error correction repairs errors at the receiver itself, from the bits that arrived — without retransmission.

The encoder turns every k-bit data block into an n-bit codeword, with n > k; the extra n−k bits are the redundancy.

The decoder checks whether the received pattern is a valid codeword; if it is not, an error is detected, and minimum-distance decoding returns the data block of the nearest codeword.

How many errors it can detect and correct hinges entirely on the code’s minimum Hamming distance d.

Module 3

Summary

CONCEPT 1 — ERROR DETECTION

Parity (single-bit check), 2-D parity (row + column + overall parity — can locate single-bit errors), and the Internet checksum (one’s-complement sum used by IPv4, TCP, UDP). Simple and fast, but limited detection power.

CONCEPT 2 — CRC

Cyclic Redundancy Check — modulo-2 division by a generator polynomial. Much stronger detection than checksums; standard at the data link layer (Ethernet, Wi-Fi). Polynomial representation lets us reason about which error patterns are guaranteed detectable.

CONCEPT 3 — ERROR CORRECTION

Forward Error Correction (FEC) — block codes with enough redundancy to correct errors, not just detect them. Hamming distance determines how many errors a code can detect and correct. Minimum-distance decoding maps an invalid codeword to the nearest valid one.
